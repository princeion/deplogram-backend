0. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
- Stack: NestJS 12 on Express 5, TypeScript 6 (ESM / nodenext), deployed as ONE
  Vercel serverless function (api/index.ts) that serves the whole app.
- There is NO database. Everything lives in one in-memory `DeplogramStore`
  (src/deplogram/store.ts), seeded on boot. Data and sessions live only as long as
  the Node process (serverless instances are ephemeral).
- The backend implements 30 `/v1/*` endpoints covering 100% of the routes that
  `deplogram-web/src/features/**` calls today, plus sign-up for the new auth pages,
  plus 23 legacy developer utility routes.
- Authentication is a cookie session (`deplogram_session`); only `/v1/me*` enforces
  it. Every other `/v1` endpoint - including mutations - is currently public.
- The deployment engine is a SIMULATION: setTimeout steps, random failures, seeded
  logs. There is no Git provider, no builder, no container registry, no CDN.
- The live frontend still defaults to MSW mocks (NEXT_PUBLIC_API_MOCKING=enabled in
  deplogram-web/.env.example); no deployed frontend project exists that points at
  this API yet.
- Biggest gaps before finalizing integration are listed in section 8.6, most notably:
  serverless in-memory state, empty /v1/traffic, incomplete deployment lifecycle,
  broken list/activity filters, missing 404s, and no authorization beyond /v1/me.

--------------------------------------------------------------------------------
1.1 Stack
  Language          TypeScript 6 (strict), ES modules, "type": "module" in package.json
  Framework         NestJS 12 (@nestjs/common, core, platform-express, swagger)
  HTTP layer        Express 5 (default Nest adapter) + cookie-parser
  Validation        class-validator + class-transformer installed; a global

                    BUT only the auth endpoints validate manually - there are no DTO
                    classes, so whitelist/transform currently do nothing for other
                    bodies. (See 8.4 B15.)
  Docs              @nestjs/swagger builds the OpenAPI 3.0 document; Swagger UI is

  Package manager   npm@10.8.2 (declared in package.json)
  Local Node        v20.19.0 (Vercel project is configured for Node 24.x)

1.2 Runtime topology
  Local dev   : src/main.ts -> NestFactory.create(AppModule) -> configureApp -> :3000
  Production  : api/index.ts -> one cached Express/Nest instance per Vercel lambda.
                vercel.json routes every path (/v1/*, /auth/*, /utils/*, /api/docs*,
                and a catch-all) to that single function.
  Implication : every invocation is independent. In-memory sessions and store writes
                do not reliably survive across requests (see 8.4 B1 / 8.6).

2. API INVENTORY
--------------------------------------------------------------------------------
2.1 Conventions
  Base paths   : /v1/* (product API), /auth/* /email/* /utils/* (legacy utilities)
  Content type : application/json (image/QR routes return binary buffers)
  Dates        : ISO 8601 strings (e.g. "2026-10-20T03:11:53.675Z")
  IDs          : prefixed strings - user_, ws_, proj_, dep_, repo_, evt_, sess_
  Sessions     : HttpOnly cookie `deplogram_session`; the web client sends
                 credentials: "include" (see section 3)
  Errors       : Nest default shape
                 {"statusCode":<n>,"message":"...","error":"..."} for HttpExceptions
                 {"statusCode":500,"message":"Internal server error"} for plain Errors
  OpenAPI      : live at /api/docs-json; UI at /api/docs (Swagger UI via CDN)

3. AUTHENTICATION AND AUTHORIZATION
--------------------------------------------------------------------------------
3.1 Flow
  Sign-in / sign-up
    Browser (credentials:"include")
      -> POST /v1/auth/sign-in|sign-up
      -> AuthController validates the body
      -> DeplogramStore.signIn/signUp -> creates a token, stores token -> userId in
         `store.sessions` (Map) and sets `store.currentUser`
      -> Set-Cookie: deplogram_session=<token>; Path=/; HttpOnly; Max-Age=2592000;
         Secure; SameSite=None   (production; Lax without Secure otherwise)
      -> 200/201 viewer JSON
  Every request
    SessionMiddleware (applied to '*') runs cookie-parser, then
    store.setCurrentUserFromSession(cookie) -> looks the token up in `sessions`.
    Controllers read `store.getViewer()` / `store.currentUser`.
  Session storage
    src/deplogram/auth/session.middleware.ts ; store.ts:374-384
    Tokens are random strings in an in-memory Map - they are NOT signed JWTs and are
    lost on process restart.

3.2 Cookie attributes
  name     : deplogram_session
  Path     : /
  HttpOnly : yes
  Max-Age  : 2592000 (30 days)
  Secure   : when NODE_ENV=production or VERCEL is set (i.e. always on Vercel)
  SameSite : None in production (needed for cross-site fetch with credentials),
             Lax locally
  Clearing : POST /v1/auth/sign-out sets the same name with Max-Age=0

3.3 CORS (src/app-config.ts:10)
  - If CORS_ORIGIN is set (comma-separated list), only those origins are allowed.
  - If unset, the caller's Origin is reflected (so `credentials: true` still works;
    the previous `origin: "*"`, which browsers reject with credentials, was fixed).
  - Allowed methods: GET, HEAD, POST, PUT, PATCH, DELETE, OPTIONS
  - Access-Control-Allow-Credentials: true

3.4 Authorization reality
  - Only AccountController checks the session (`signedIn()`, account.controller.ts:31).
    Every other `/v1` route - including create/update/delete of projects, env vars,
    deployments, redeploy, rollback - is OPEN. Verified: POST /v1/projects without a
    cookie returns 201; GET /v1/workspace without a cookie returns 200.
  - There are no roles, permissions, teams or workspace membership checks. The store is
    a single global dataset; `currentUser` is set per request purely for attribution
    (activity actor, project creation) and for /v1/me.
  - No CSRF protection on cookie-authenticated mutations.

3.5 Gaps / risks (see also section 7)
  - Authorization must be added before any shared deployment (IMPLEMENTED none beyond
    /v1/me). Open decision: session-scoped guards vs. API tokens (section 9).
  - Passwords are plain text; sessions are unsigned in-memory tokens.
  - Default CORS reflection + cookie auth is permissive; set CORS_ORIGIN in production.
  - No rate limiting / lockout on sign-in.

5. DEPLOYMENT ENGINE ARCHITECTURE
--------------------------------------------------------------------------------
5.1 What exists today: a simulation, not an engine
  The only "engine" is `DeploymentService` (src/deplogram/deployments/deployments.service.ts)
  plus the store helpers it calls. There is:
    - no Git clone/fetch (Git endpoints are seeded data),
    - no build runner, no container runtime, no image registry,
    - no CDN/static hosting, no domain provisioning, no TLS,
    - no infrastructure provider integration (Vercel/Fly/AWS/K8s/Firecracker/etc.),
    - no scheduler/worker/queue.
  A "build" is a chain of setTimeout calls inside a serverless request handler.

5.2 State machine (per the contract in types.ts:14-30)
  QUEUED -> BUILDING -> BUILT -> DEPLOYING -> RUNNING        (success)
          \-> BUILD_FAILED                                   (build failure)
                            \-> DEPLOY_FAILED                  (deploy failure)
  CRASHED is declared but never produced by the simulator.
  PRODUCT GAP: the simulator never assigns BUILDING, BUILT or DEPLOYING to
  `deployment.state`. The state stays QUEUED until it jumps to RUNNING or a failure
  (deployments.service.ts startBuild/finishBuild). So the UI never sees the middle
  states from the API (only `steps` change). (B11)

5.3 Build steps and timing (startBuild, service.ts:163)
  Steps, in order: clone, install, build, deploy, runtime
  Delay: 900 ms per step; runtime 400 ms -> ~4 s total
  Random failures: build 15%, deploy 10%
  Step objects carry {id,label,state,startedAt,endedAt}; they live in an in-memory Map
  on the service instance and are DELETED when the build settles (`builds.delete`), so
  GET .../logs returns `steps: []` once `done` is true.
  No build log LINES are produced by the simulator. (B12)

5.4 Supported runtimes
  The runtime set is defined by the frontend (deplogram-web/src/content/runtimes.ts):
    id      name        default build command          default start        default port
    vite    Vite        npm run build                  (static output)      -
    nextjs  Next.js     npm run build                  npm start            3000
    node    Node.js     npm run build                  node server.js       8080
    python  Python      pip install -r requirements    uvicorn main:app     8000
    php     PHP         composer install               php artisan serve    8000
    go      Go          go build -o app                ./app                8080
    static  Static      (optional)                     (static files)       -
    docker  Docker      docker build .                 CMD from Dockerfile  EXPOSE
  Backend behaviour:
    - Project/Deployment store whatever `runtime` string they are given (no validation).
    - `config.runtimeVersion` is derived by store.defaultRuntimeVersion (store.ts:940):
      nextjs -> "22.14.0", node -> "22.x", python -> "3.12", php -> "8.3", go -> "1.23",
      anything else -> "latest". Note nextjs returns a Node version string.
    - Runtime detection (git/detect) only ever returns nextjs (repo_storefront) or node
      (repo_api); the `branch` argument is ignored.

5.5 Logs
  Build logs   : `buildLog` Map; seeded lines only; cursor is the 1-based `n`.
                 GET /v1/deployments/:id/logs?after=n returns lines after n, plus step
                 states, plus `done`.
  Runtime logs : `runtimeLog` Map; one seeded line for each live seeded deployment.
                 GET /v1/projects/:id/logs?after=n returns the live deployment's log +
                 `live` (true while a deployment is live). Nothing appends new lines.
  No log streaming (SSE/WebSocket) exists; the frontend polls (1s build, 1.5s runtime).

5.6 URLs and live marking
  store.urlOf (store.ts:936) returns `https://<projectName>.deplogram.app` - i.e. a full
  URL, whereas the frontend treats `ProjectSummary.url` / `Deployment.url` as a HOST and
  prepends `https://` itself -> broken links (B8).
  `markLive` (store.ts:694) unsets `live` on the project's other deployments, sets
  state=RUNNING, url, project.liveDeploymentId and project.state=RUNNING. It is called
  ONLY by the seed and by rollback - never by a finished build (B3).
  `durationSeconds` is set only for failures (finishDeployment, store.ts:734); successful
  RUNNING deployments keep null (B10).

5.7 Traffic, metrics and usage generation
  - TrafficPoint access log is intended to feed /v1/traffic and project metrics, but
    nothing calls `appendRequest` -> both are empty/zero (B5).
  - Metrics are computed from the access log (bucket sizes 5min/1h/6h for 1h/24h/7d);
    p50/p95 via nearest-rank percentile; cpu/memory hard-coded 0; memoryLimit 512 (MB).
  - Usage is derived from deployments + requests with placeholder maths (see 2.3).

5.8 Serverless caveat (critical)
  setTimeout-based builds do not survive a serverless response. Verified in production:
  POST /v1/deployments/dep_live/redeploy returned a QUEUED deployment that was STILL
  QUEUED 6 seconds later. Combined with the in-memory store, the deployment engine only
  works in a long-lived process (local dev) and only while the same instance stays warm.

5.9 Status summary
  IMPLEMENTED (simulated) : seeded project/deployment data, build-step state machine,
                            build log cursor read API, redeploy/rollback endpoints exist
  PARTIAL                 : lifecycle states, live marking, duration, logs, traffic
  PLANNED / NOT DECIDED   : real Git integration, real builder, container runtime,
                            registry, CDN/static hosting, DNS/TLS, autoscaling,
                            observability - all open (section 9)

7. SECURITY, LIMITS, JOBS AND INFRASTRUCTURE DEPENDENCIES
--------------------------------------------------------------------------------
7.1 Security measures present
  - HttpOnly session cookie; Secure + SameSite=None in production; Lax locally.
  - CORS with credentials; origin reflection by default, allow-list via CORS_ORIGIN.
  - Auth body validation (sign-up: name/email/password rules; sign-in presence checks).
  - SIGN_IN_ENABLED kill switch for sign-in (not sign-up).
  - Plain-text secrets: none committed; config comes from environment variables.

7.2 Security gaps / risks (must be closed before a real launch)
  - No authorization on any /v1 route except /v1/me* (section 3.4). Anyone can create,
    rename, delete projects, edit env vars, redeploy/rollback, and read all data.
  - Passwords stored in plain text (store.ts:93, signUp store.ts:337); sessions are
    unsigned random tokens in memory.
  - No CSRF protection for cookie-authenticated mutations; CORS defaults to reflecting
    any origin -> a malicious site could call the API with the victim's cookie.
  - No rate limiting, account lockout, or abuse protection.
  - No request-body validation on mutations (no DTOs) -> malformed bodies can corrupt
    state or throw 500s.
  - Env var values stored in plain text; no encryption/KMS; `PUT env` returns only keys.
  - SSRF: POST /utils/webhook/test makes an outbound HTTP request to any caller-supplied
    URL, including internal addresses (src/webhook-tester.service.ts).
  - OTP codes are logged and emails default to smtp.example.com (demo only).
  - No security headers (helmet/CSP); Swagger UI loads JS from a third-party CDN.
  - No audit integrity: activity actor is just `currentUser` on a public endpoint.

7.3 Resource limits
  - activityOrder capped at 500 events; access log capped at 5000 points (unused today).
  - No caps on users, sessions, projects, deployments, env vars, or log lines per
    deployment; logs for deleted projects are never freed.
  - `pageSize` on /v1/deployments has no upper bound.
  - Express 5 default JSON body limit (~100 KB) applies; the JSON-body image/QR utility
    routes need larger payloads.
  - Vercel: 2 cores / 8 GB build, serverless execution/memory limits, ephemeral disk.

7.4 Queues / background jobs
  - None. There is no queue, worker, cron or job runner.
  - The only background work is the setTimeout build simulation (section 5), which does
    not survive serverless responses.
  - No retries, no idempotency keys, no at-least-once delivery.

7.5 Infrastructure dependencies (current)
  - Vercel serverless functions (@vercel/node) + Vercel routing (vercel.json).
  - In-process memory only (the store) - no DB, cache, queue or object storage.
  - SMTP (nodemailer) for /email/send - unconfigured by default.
  - sharp (native) and qrcode for image/QR utilities.
  - jsdelivr CDN for Swagger UI assets.
  - GitHub only as the source repo (no API integration at runtime).

7.6 Environment variables
  PORT             default 3000 (local)
  CORS_ORIGIN      comma-separated allowed origins (unset -> reflect request origin)
  SIGN_IN_ENABLED  "false" disables sign-in
  JWT_SECRET       legacy /utils/jwt/* only (default "secret-key")
  EMAIL_HOST/PORT/SECURE/USER/PASS/FROM   /email/send (defaults to smtp.example.com)
  NODE_ENV / VERCEL   determine cookie Secure/SameSite
  Current deployed state: the Vercel project has NO environment variables set, so CORS
  reflects any origin and emails would fail.

8.4 Known bugs (severity: H/M/L, with evidence)
  B1  H  In-memory store + serverless: all state and sessions are per-instance and can
         vanish between requests; setTimeout builds are frozen after the response.
         Evidence: a production redeploy was still QUEUED after 6s.
         Files: api/index.ts, store.ts, deployments.service.ts.
  B2  H  POST /v1/projects creates a first deployment but never starts its build.
         Files: projects.service.ts:37-56 (no call to startBuild).
  B3  H  A finished build never becomes live: finishBuild sets RUNNING but does not call
         markLive, so no url, and the previous live deployment stays live.
         Files: deployments.service.ts:244-249 ; store.ts:694.
  B4  H  Rollback semantics are inverted vs. the frontend: it promotes id.previousLiveId
         instead of the passed (earlier, non-live RUNNING) deployment, creates no new
         deployment, and returns the wrong `deployment`. The existing test encodes the
         wrong behaviour.
         Files: deployments.service.ts:136-152 ; store.ts:712-733 ;
         frontend deplogram-web/src/mocks/data/deployments.ts:209.
  B5  H  The traffic access log is never written (appendRequest has no callers), so
         /v1/traffic is always empty and metrics are all zero. Files: store.ts:856.
  B6  M  /v1/deployments filters: `status` groups don't exclude non-matches, and
         comma-separated status/project/branch/trigger values are not split.
         Evidence: ?status=failed returned all 4 deployments; ?project=a,b returned 0.
         Files: deployments.service.ts:59-95 ; deployments.controller.ts:61.
  B7  M  /v1/activity ignores `type` and `project` (accepted then dropped).
         Files: activity.controller.ts:17-23.
  B8  M  `url` is returned with the scheme (https://x.deplogram.app) while the frontend
         prepends "https://" -> broken links.
         Files: store.ts:936 ; frontend use-deployment-actions.tsx:85 etc.
  B9  M  Wrong error semantics: unknown project id -> 200 empty (exists? no), unknown
         deployment/logs/metrics -> 500 instead of 404; DELETE unknown project -> 204;
         PUT env unknown -> 200 []. Files: projects.controller.ts:50-85 ;
         deployments.controller.ts:19-32 ; service throw sites.
  B10 M  durationSeconds stays null for successful RUNNING deployments (only failures get
         a duration), so the UI shows "running..." forever.
         Files: store.ts:734-749.
  B11 M  DeploymentState BUILDING/BUILT/DEPLOYING are never emitted by the simulator.
         Files: deployments.service.ts:163-249.
  B12 M  Simulated builds produce no log lines and delete their step list when finished
         (steps: [] with done: true). Files: deployments.service.ts (no appendBuildLog),
         builds.delete at 253.
  B13 L  test/app.e2e-spec.ts is stale and fails (expects GET / -> 200 "Hello World!").
  B14 L  The backend uses the host suffix "deplogram.app"; the frontend mock uses
         "dpl.app". Product decision needed (the backend value is authoritative once the
         domain model is set).
  B15 L  No DTO classes -> the global ValidationPipe does nothing for most bodies;
         malformed PATCH bodies can throw 500s.
  B16 M  POST /v1/projects does not enforce unique names (duplicates accepted).
  B17 L  PATCH /v1/projects/:id always records activity type `project.renamed`, even for
         branch/config-only changes.
  B18 L  Sign-up is not covered by SIGN_IN_ENABLED, and there is no rate limiting.

8.6 Immediate blockers before finalizing frontend/backend integration
  1. Persistence + a place to run background builds (Postgres/Redis + a worker/queue, or
     a long-lived service). In-memory + serverless cannot run the product.
  2. Authorization on all /v1 mutations and per-user data isolation.
  3. Fix the deployment lifecycle: start builds for new projects, emit BUILDING/BUILT/
     DEPLOYING, mark live on success, set duration, write build/runtime log lines.
  4. Fix rollback to match the frontend contract (promote the chosen deployment, create a
     new rollback deployment, return previousLiveId of the old live one).
  5. Generate traffic (or wire the real access log) so /v1/traffic and metrics work.
  6. Fix list/activity filters and return 404s (and 409/422 where the UI expects them).
  7. Fix `url` to be a host (or update the frontend) - one side only.
  8. Decide and implement the realtime channel + the frontend env switch to the real API.

  Phase 3 (architecture): database + migrations, real auth/authorization, secrets

  Phase 4 (frontend): wire sign-up (hook + MSW handler), set NEXT_PUBLIC_API_URL,
    disable mocking, deploy and run the contract tests against production.
